# Main Menu 3D Stage

## Intent

The main menu is presented from the drummer's side of an original concert
stage. The drum kit occupies the foreground, while an audience faces the kit
from beyond the riser. Truss lights, video walls, speaker stacks, runways, haze,
and a moving crowd create depth without competing with the menu on the left.

This is a real-time Unity scene, not a pre-rendered background. The previous
`stage-command.png` remains available only as a defensive fallback if the 3D
environment cannot initialize.

## Composition

The view deliberately uses an asymmetric composition:

- the UI owns the left side and remains readable over a translucent scrim;
- the kick, toms, cymbals, and neon drum riser read on the right;
- the camera sits behind and above the drummer, looking toward the audience;
- two side video walls leave the central audience sightline open;
- six crowd rows recede into the venue to establish scale;
- six moving heads and three audience fill lights separate foreground,
  midground, and background;
- speaker stacks and side runways frame the playable stage.

The venue remains deliberately economical, but the hero drum kit uses an HD
hard-surface treatment: high-segment shells, independent drum heads and bearing
edges, paired hoops, individual lugs and tension rods, articulated stands,
pedal mechanisms, curved cymbal profiles, felts, wing nuts, rack mounts, and
physically supported floor hardware. The audience uses 130 original procedural
human characters rather than abstract capsules. Every figure has a complete
body silhouette, jointed two-segment limbs, hands, shoes, facial volume, hair,
and one of seven concert poses; selected spectators also hold illuminated
phones. Skin, hair, clothing, shoes, and small facial details remain separate
material roles so stage lighting reveals people without stealing focus from
the drum kit.

## HD drum-kit reference

The visual target was established with an original generated product-style
reference:

```text
docs/design/references/modern-drum-kit-hd-concept.png
```

The image defines proportions, material separation, hardware density, and the
graphite/chrome/bronze finish. It is a modeling reference, not a texture or a
billboard used by Unity. The runtime kit remains original procedural geometry
and can be regenerated without an image-generation service.

## Original Blender asset

All geometry is original and generated by
`tools/blender/create_main_menu_stage.py`. It uses only Blender primitives and
contains no downloaded meshes, textures, logos, or third-party artwork. The
reference image and the procedural mesh were created specifically for this
project.

The procedural source, local editable file, and runtime model are:

```text
tools/blender/create_main_menu_stage.py
artifacts/main-menu-stage/HitTheKit-MainMenuStage.blend  (local, ignored)
src/HitTheKit.Unity/Assets/HitTheKit/Visuals/Models/HitTheKit-MainMenuStage.fbx
```

Regenerate both files with Blender 5.2 LTS:

```shell
./scripts/build-main-menu-stage-assets.sh
```

The script can be run from any working directory. Geometry is generated from a
fixed random seed, so object names, hierarchy, transforms, and crowd placement
are repeatable. The generated `.blend` is deliberately ignored: Blender embeds
its absolute save location, while the Python generator is a smaller,
reviewable, path-independent source of truth. Blender also embeds export
metadata in the FBX container, so byte-identical hashes across separate
invocations are not a guarantee; Unity-visible scene content is the
reproducibility contract.

### Naming boundary

Renderer names encode presentation roles rather than gameplay rules:

```text
DrumShell_  DrumHead_  DrumInterior_  Cymbal_  Chrome_  Hardware_
Stage_      Fixture_   Accent_
Audience_Skin*  Audience_Clothes*  Audience_Hair*
Audience_Shoes_  Audience_Detail_  Audience_Accent_
```

`MainMenuSceneBuilder` maps these prefixes to shared URP materials. There is no
instrument mapping, MIDI note, scoring, or gameplay behavior in the Blender
asset.

## Unity composition

`MainMenuSceneBuilder` imports the FBX and generates
`MainMenuPrototype.unity` through Editor APIs. The scene contains:

- one HDR perspective camera;
- the imported stage model;
- two directional lights;
- six animated spotlights;
- three audience fill lights;
- a bounded atmosphere particle system;
- the existing UIDocument and menu controller.

`MainMenuPanelSettings.asset` is intentionally separate from Device Setup. Its
color and depth clears are disabled so UI Toolkit overlays the camera instead
of erasing the 3D frame. The static menu image is hidden only after
`MainMenuStageEnvironment` reports a valid camera and model root.

## Runtime behavior

`MainMenuStageEnvironment` owns presentation-only animation:

- slow, bounded spotlight sweeps;
- subtle row-based audience sway;
- a very small camera drift;
- a short light pulse when the selected destination changes;
- theme-driven material and light palettes;
- immediate restoration of base transforms when reduced motion is enabled.

Animation uses unscaled time and does not influence menu navigation, audio,
MIDI, timing, or gameplay state. No renderer allocates a private material at
runtime; colors use `MaterialPropertyBlock` over shared materials.

## Themes

The stage follows the same persisted presentation setting as gameplay:

- **Arcade Neon** — cyan/magenta, cool chrome, blue audience wash;
- **Concert Stage** — amber/red lighting and warmer metal;
- **Precision Grid** — teal/green, lower-energy technical lighting.

Changing the theme in Settings updates the existing scene. It does not load a
second model or create a separate main-menu implementation.

## Accessibility and performance

- The UI retains keyboard focus, labels, and contrast independently of the 3D
  background.
- Reduced Motion freezes camera, spotlight, and audience transforms.
- Important state is never communicated only through stage color or motion.
- Character parts are batched by material within each row, while crowd motion
  remains limited to six row transforms.
- Atmosphere is capped at 260 particles.
- The model uses shared PBR materials and no external runtime textures.
- The fallback image remains available for unsupported or incomplete loads.

## Verification

The automated boundary checks cover:

- stage initialization and renderer count;
- six crowd rows and six moving spotlights;
- transparent main-menu PanelSettings;
- static-image fallback suppression only when the stage is ready;
- distinct palettes and runtime theme propagation;
- reduced-motion and existing main-menu navigation behavior.

The standalone macOS player is the final visual check because it exercises the
same URP, UI Toolkit overlay, import settings, and camera composition that the
user sees outside the Editor.
